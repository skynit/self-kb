# 网络穿透部署检查与故障排查

返回 [[70-项目/01-CWNAS/02-相关知识/网络穿透/00-网络穿透知识导航|知识导航]]。

本文给出排查方法与命令示例，**未对 CWNAS 当前服务器、NAS 或生产网络执行检查**。`nas.example.net` 和 `203.0.113.80` 是文档示例目标，实际使用时替换成有权限排查的服务地址。

## 1. 先确定失败停在哪一步

建议将一次请求归入下列阶段，沿最近的失败点排查：

```text
目标与授权
  → DNS/平台连接
  → 信令登记和消息交换
  → 候选收集与检查
  → DTLS/SCTP/DataChannel
  → 设备身份与 NAS 登录
  → 具体业务请求
```

该顺序结合 ICE 和 WebRTC 协议阶段，并加入产品身份与业务步骤。不同实现可能让候选收集和协商并行，排查不要求日志严格按上图逐条串行出现。[^S11][^S19]

| 现象 | 优先核对 | 不宜直接下的结论 |
| --- | --- | --- |
| 平台域名打不开 | DNS、路由、代理、TLS、平台入口 | NAT 类型有问题 |
| 信令在线但目标不存在 | 目标标识、登记、连接归属、在线状态 | TURN 端口没开放 |
| 没有 `srflx` | STUN 可达性、实际配置、收集策略、错误事件 | 整个连接必定失败 |
| 没有 `relay` | TURN 配置是否在收集时生效、认证、入口可达性、策略 | 一定只是密码错 |
| 已有 `relay` 但检查不通 | 中继地址、端口范围、Permission、对端及双向网络 | TURN 已完全正常 |
| ICE 成功但通道未打开 | DTLS、证书指纹、SCTP、通道协商 | NAS 用户权限不足 |
| 通道打开但业务拒绝 | 设备身份、登录、权限、应用协议 | 网络穿透没打通 |
| 小请求成功、大文件停顿 | 分块、背压、消息大小、吞吐、代理超时、路径 MTU | 增加心跳就能解决 |

**路径 MTU** 是整条路径上不需要分片即可承载的包大小上限，由链路和封装共同约束；它与应用单条 DataChannel 消息大小不是同一个概念。表中的排查方向来自协议机制的组合推导，现场仍须用日志和抓包验证。[^S13][^S15][^S16]

## 2. 记录环境与拓扑

排查前记录以下信息，便于把两端和平台日志对到同一条连接：

- 访问端、NAS、平台的系统、应用/浏览器/通信库版本及时间。
- 两端所在网络：同一局域网、不同家庭网络、移动网络、公司网络等。
- 家庭网关是否还有上游 NAT，双方是否可用 IPv4/IPv6。
- 信令入口、STUN/TURN 地址、入口协议、证书名称及中继地址配置。
- 本次会话编号、失败阶段、错误码、选中候选对或没有选中的事实。

时钟对于短期凭据与证书验证尤其相关；遇到认证异常时，应比较设备和服务端时间，而不是仅延长凭据期限。动态凭据的格式和时效语义按实际服务实现核对。[^S29]

## 3. 主机侧检查：地址、路由、监听

以下命令适用于常见 Linux 环境，分别由 iproute2 的 `ip` 和 `ss` 工具提供。`ip` 查询接口地址与路由，`ss` 查询 socket；它们不等于业务连通性测试。[^S30][^S31][^S32]

```bash
# 查看接口及 IPv4/IPv6 地址。
ip -brief address

# 分别查看两个地址族的路由。
ip route
ip -6 route

# 查询系统准备如何到达某个目标；不实际证明目标响应。
ip route get 203.0.113.80

# 查看 TCP 监听。
ss -ltnp

# 查看 UDP 绑定及相关进程。
ss -lunp
```

参数 `-l` 关注监听/接收用的 socket，`-t`/`-u` 分别选择 TCP/UDP，`-n` 保留数字地址和端口，`-p` 显示可见的进程信息。当前用户权限不足时可能看不到其他用户的进程。UDP 没有 TCP 那种监听握手状态，`ss` 中出现 socket 也只证明本机绑定，不能证明外网收得到。[^S32]

检查监听地址时，区分只绑定回环地址、绑定特定接口、绑定 IPv4 或 IPv6 的情况；同时核对主机防火墙、云平台入站/出站规则及前置 NAT。**云安全组** 是云平台为实例或网卡配置的流量规则，由云管理员维护，和主机内的防火墙是两层控制。

## 4. HTTPS 检查能证明多少

```bash
# 使用 HEAD 请求检查示例 Web 入口；按实际服务路径替换。
curl --connect-timeout 5 --max-time 10 -I https://nas.example.net/
```

`--connect-timeout` 限制连接建立阶段，`--max-time` 限制整个操作；`-I` 请求响应头。部分服务不支持 HEAD，返回 405 等状态仍需结合实际接口解释。TLS 校验默认保留，避免掩盖域名或证书问题。[^S33]

这个命令只能检查该 HTTPS 请求路径。它不证明 WebSocket 升级、STUN/UDP、TURN Allocate 或 DataChannel 可以正常工作；反过来，TURN 入口也不是一个可以用普通 HTTP 请求完整验证的服务。[^S13][^S19]

## 5. TURN 专项：逐段验证

| 检查项 | 为什么检查 | 可接受的证据 |
| --- | --- | --- |
| 客户端配置 | 地址、协议、用户名及凭据必须对应目标服务 | 本次连接使用的脱敏配置、版本和收集错误 |
| 入口连通 | 客户端必须能连接所选 UDP/TCP/TLS 入口 | 服务接到请求、客户端得到合法响应 |
| 认证 | 挑战后请求必须通过验证 | Allocate 成功；区分初始 401 和最终失败 |
| 中继地址 | 返回给客户端的地址须可从相关网络到达 | Allocate 响应、外部地址与 NAT 映射配置一致 |
| 中继端口 | 对端数据需要到达分配的 socket | 指定分配的收发包、主机及云规则匹配 |
| Permission/Channel | 必须允许预期对端并有有效状态 | 协议日志或相应成功响应 |
| 数据往返 | 有资源不代表有成功传输 | 对端收到内容、回包成功、字节计数增加 |
| 刷新和回收 | 长连接依赖状态刷新，关闭后资源应释放 | 生命周期事件、刷新成功和资源回落 |

检查项依据 TURN 协议与 coturn 的部署说明。中继端口范围由实际部署者配置，不能把某份教程中的 `49152–65535` 或项目历史端口当作固定协议要求。[^S13][^S29]

**中继强制验证方法：** 在受控诊断中将客户端设为只用中继候选，重新创建或按接口要求协商连接，完成小文件传输及内容校验，并记录选中候选对和中继字节变化。该方法验证已配置中继的业务闭环；恢复正常策略后，再独立观察直连能力。它是一项建议验收场景，本次未执行。[^S19][^S20]

## 6. 浏览器侧查看实际连接

浏览器可以使用 `RTCPeerConnection.getStats()`；Chromium 系浏览器通常也提供 `chrome://webrtc-internals` 等诊断页面。浏览器内部页面和展示字段会随产品变化，以可用接口统计为准。[^S19][^S20][^S35]

建议在业务传输前后各采一次：

1. 找到 transport 的 `selectedCandidatePairId`。
2. 找到对应 candidate-pair 记录及其本地、远端候选 ID。
3. 读取两个候选的 `candidateType`，检查是否涉及 `relay`。
4. 比较同一统计对象的收发字节增量及采样时刻。
5. 同时关联设备认证和业务结果，判断问题出在通道还是上层。[^S20]

**没有 `relay` 的选中对**可说明该 WebRTC 选中路径未使用 TURN 候选；它不保证物理路由“完全没有任何其他代理或隧道”。同理，不要用服务器仍保留的闲置 allocation 来覆盖端点的路径证据。[^S11][^S20]

## 7. 抓包：定位数据在哪一段消失

**抓包** 是在特定接口观测实际收发的网络报文，由 `tcpdump` 等工具执行；它帮助观察地址、协议、方向和时间，不自动理解应用加密后的文件内容。下面仅显示与示例目标相关的最多 100 个包，运行需要相应抓包权限。[^S34]

```bash
tcpdump -ni any -nn -c 100 'host 203.0.113.80 and (udp or tcp)'
```

`-i any` 选择可用的综合接口，`-n/-nn` 避免地址与端口名称解析，`-c 100` 在收到指定数量的匹配包后退出。若始终没有匹配包，计数不会达到上限，可手动中止。[^S34]

建议针对具体 socket 和会话逐段对照：

```text
客户端发出
  → TURN 入口收到
  → TURN 中继端口发出
  → NAS/对端收到
  → NAS/对端回包
  → 中继收到并交回客户端
```

在 NAT 后抓到的本地地址可能与公网观测地址不同，应按照映射关系对应。只看到一个方向的包时，继续查下一跳、过滤规则和回程路由，不立即归因于客户端。排查记录可保存脱敏元数据与必要片段，避免将带令牌的完整协商或业务内容粘贴到公共问题中。

## 8. 大文件卡住时的排查顺序

1. **应用状态**：读文件、编码、写盘或权限是否卡住；请求是否已经取消。
2. **发送缓冲**：待发送缓冲是否不断增长；发送方是否实现背压和消息大小约束。
3. **通道与传输**：连接状态、吞吐、RTT、丢包相关迹象；对比直接路径和强制中继。
4. **网络封装**：中继 TCP/TLS 的队头等待、路径 MTU、VPN/代理叠加等因素是否存在。
5. **资源上限**：服务器带宽、CPU、文件描述符、分配配额和端口资源。

**队头等待** 指较早的数据因丢失或阻塞无法交付，使后续数据一起等待的现象；在可靠有序传输及多层封装中要结合具体协议判断，不能简单把所有卡顿都称作 UDP 丢包。以上是分层排查建议，数据通道的消息与拥塞机制见 RFC 8831。[^S15][^S16]

## 9. 建议的最小验收矩阵

本表是后续部署时可采用的检查范围，不是本次执行结果。

| 场景 | 要证明什么 |
| --- | --- |
| 同一局域网 | 本地候选和业务身份链路可用 |
| 两个不同家庭网络 | 实际直接路径或中继路径可完成业务 |
| 移动网络到家庭 NAS | 多层 NAT 环境的成功率和中继可用性 |
| 强制中继 | 中继认证、分配、端口、双向传输和计量完整 |
| 长时间空闲后再请求 | 刷新、保活及失败恢复符合设计 |
| 传输中切换网络 | 应用的重连、取消或续传行为清楚且可验证 |
| 错误凭据或无文件权限 | 失败发生在正确层次，错误可诊断 |
| 传输取消并关闭 | 通道、分配及本地文件资源按设计回收 |

“成功”至少包含：选中路径明确、预期设备身份通过、目标业务完成、内容一致、关闭后资源回落。单独的进程存活、端口监听或信令在线只覆盖其中很小的一部分。
