# 网络穿透参考资料

返回 [[70-项目/01-CWNAS/02-相关知识/网络穿透/00-网络穿透知识导航|知识导航]]。

查阅日期：**2026-10-21**。正文脚注与本页编号对应。URL 保留在行内代码中，便于复制和在浏览器打开；全部协议解释优先采用标准原文，工具能力采用官方文档。以下说明均为阅读指引和中文归纳。

## 资料性质与阅读方式

- **IETF / RFC Editor**：IETF 是制定互联网技术规范的开放组织，RFC Editor 负责 RFC 的编辑和发布。RFC 并不全部等于互联网标准；下列文档包括最佳当前实践、标准轨文档和信息性说明。
- **W3C**：制定 Web 平台规范的组织。WebRTC 接口和统计文档描述浏览器可调用的对象与字段；应同时留意文档发布状态和实现差异。
- **工具官方文档**：描述相应项目的能力与参数，内容可能持续更新；部署时结合版本核对。
- **项目历史笔记**：提供当时的实现证据，不自动代表当前源码或线上状态。

建议顺序：先 S03/S04/S07，再 S10/S11/S13，然后 S15/S17/S19/S20，最后按方案阅读工具文档。

## S01

**RFC 1918 — Address Allocation for Private Internets**。性质：最佳当前实践。

原文：`https://www.rfc-editor.org/rfc/rfc1918.html`

重点：第 3 节，三个私有 IPv4 地址范围。用于区分私网寻址和可供全球互联网路由的地址。

## S02

**RFC 6598 — IANA-Reserved IPv4 Prefix for Shared Address Space**。性质：最佳当前实践。

原文：`https://www.rfc-editor.org/rfc/rfc6598.html`

重点：`100.64.0.0/10` 共享地址空间及运营商级 NAT 场景；它与 RFC 1918 私网地址不是同一个分配类别。

## S03

**RFC 2663 — IP Network Address Translator (NAT) Terminology and Considerations**。性质：信息性文档。

原文：`https://www.rfc-editor.org/rfc/rfc2663.html`

重点：Basic NAT、NAPT、地址绑定、会话和转换术语。适合建立“路由、地址转换、端口转换”的基础模型。

## S04

**RFC 4787 — Network Address Translation (NAT) Behavioral Requirements for Unicast UDP**。性质：最佳当前实践。

原文：`https://www.rfc-editor.org/rfc/rfc4787.html`

重点：第 4 节映射、第 5 节过滤、第 6 节回环；理解为什么端口映射行为与允许回包的条件必须分开描述。

## S05

**RFC 7857 — Updates to Network Address Translation (NAT) Behavioral Requirements**。性质：最佳当前实践。

原文：`https://www.rfc-editor.org/rfc/rfc7857.html`

重点：对 UDP、TCP、ICMP NAT 行为要求的更新，包含映射和端口相关细节。阅读早期 NAT 文档时需要注意这些修订。

## S06

**RFC 5382 — NAT Behavioral Requirements for TCP**。性质：最佳当前实践。

原文：`https://www.rfc-editor.org/rfc/rfc5382.html`

重点：TCP NAT 的连接状态、同时打开和过滤行为要求；用来说明 TCP 打洞不能直接照抄 UDP 发包过程。

## S07

**RFC 5128 — State of Peer-to-Peer (P2P) Communication across Network Address Translators (NATs)**。性质：信息性文档。

原文：`https://www.rfc-editor.org/rfc/rfc5128.html`

重点：中继、反向连接和 UDP/TCP 打洞的思路及条件。是理解方法的背景材料，不应当作某工具当前实现或成功率承诺。

## S08

**RFC 6092 — Recommended Simple Security Capabilities in Customer Premises Equipment (CPE) for Providing Residential IPv6 Internet Service**。性质：信息性文档。

原文：`https://www.rfc-editor.org/rfc/rfc6092.html`

重点：家庭 IPv6 网关的状态过滤建议。CPE 指部署在用户场所的网关等设备，可由运营商提供或用户自行配置；它与云端中继服务器不是同一角色。

## S09

**RFC 6887 — Port Control Protocol (PCP)**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc6887.html`

重点：客户端向支持的网关请求映射/放行及生命周期管理；附录讨论与已有自动映射机制的关系。

## S10

**RFC 8489 — Session Traversal Utilities for NAT (STUN)**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8489.html`

重点：Binding、`XOR-MAPPED-ADDRESS`、消息完整性、认证及 STUN 作为工具的边界。它取代早期 RFC 5389；不应再以 RFC 3489 的旧式 NAT 分类作为完整现代行为模型。

## S11

**RFC 8445 — Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8445.html`

重点：候选收集、候选对、角色、连通性检查、提名、选中路径及重启。它取代 RFC 5245；阅读时需区分完整 ICE 流程与产品宣传中的“先打洞后中继”。

## S12

**RFC 8838 — Trickle ICE: Incremental Provisioning of Candidates for the Interactive Connectivity Establishment (ICE) Protocol**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8838.html`

重点：增量发送候选、检查启动及候选收集结束信息。适合理解为什么候选与会话描述的时序需要管理。

## S13

**RFC 8656 — Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8656.html`

重点：Allocate、Refresh、Permission、ChannelBind、Send/Data Indication、ChannelData、认证和资源安全。它取代 RFC 5766；客户端入口传输与中继侧传输需要分别理解。

## S14

**RFC 7065 — Traversal Using Relays around NAT (TURN) Uniform Resource Identifiers**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc7065.html`

重点：`turn:`、`turns:`、传输参数及默认端口。URI 表达服务连接方式，不等于创建了一条成功的中继业务路径。

## S15

**RFC 8831 — WebRTC Data Channels**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8831.html`

重点：SCTP over DTLS、消息与流、可靠性、拥塞控制、优先级及大消息影响。用于解释文件传输为什么还要设计分块、排队与恢复。

## S16

**RFC 8835 — Transports for WebRTC**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8835.html`

重点：WebRTC 的 ICE、UDP、TURN、TCP/TLS 路径及网络限制处理；说明应用协议层与实际网络传输之间的关系。

## S17

**RFC 8827 — WebRTC Security Architecture**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8827.html`

重点：信令与媒体/数据传输、安全身份及信任模型。用于区分加密通道、预期设备身份和应用业务权限。

## S18

**RFC 7675 — Session Traversal Utilities for NAT (STUN) Usage for Consent Freshness**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc7675.html`

重点：持续确认对端同意接收数据的机制。Consent Freshness 是由协议栈执行的同意状态维护，和应用层“用户仍登录”或简单单向保活不是同一概念。

## S19

**W3C — WebRTC: Real-Time Communication in Browsers**。

原文：`https://www.w3.org/TR/webrtc/`

本次读取的发布页标注为 W3C Recommendation，发布日期为 2025-03-13。

重点：`RTCPeerConnection`、`RTCConfiguration`、`setConfiguration()`、描述与候选接口、`restartIce()`、DataChannel 状态和缓冲管理。该地址指向发布页，文档会持续演进，注意实现兼容性。

## S20

**W3C — Identifiers for WebRTC's Statistics API**。

原文：`https://www.w3.org/TR/webrtc-stats/`

本次读取的发布页标注为 Candidate Recommendation Draft，发布日期为 2025-09-25；属于仍在演进的候选推荐标准草案，字段还需结合浏览器实现核对。

重点：`RTCTransportStats.selectedCandidatePairId`、candidate-pair、本地/远端候选、字节和 RTT 等字段。优先依据对象关联寻找选中路径，不根据候选列表猜测。

## S21

**frp — Concepts**。

官方文档：`https://gofrp.org/en/docs/concepts/`

重点：服务端 `frps`、客户端 `frpc`、代理、visitor 等角色。角色名称是 frp 的配置概念，不是全部穿透系统通用的同名组件。

## S22

**frp — STCP & SUDP**。

官方文档：`https://gofrp.org/en/docs/features/stcp-sudp/`

官方配置示例：`https://gofrp.org/en/docs/examples/stcp/`

重点：私有服务、visitor、本地访问端口和密钥配置；用来区分私有转发和公开 Web 入口。

## S23

**frp — XTCP / P2P**。

官方文档：`https://gofrp.org/en/docs/features/xtcp/`

中文说明：`https://gofrp.org/zh-cn/docs/examples/xtcp/`

重点：点对点访问条件、NAT 限制与回退思路。按实际版本确认底层传输及具体参数。

## S24

**WireGuard — Quick Start**。

官方文档：`https://www.wireguard.com/quickstart/`

重点：接口、peer、公钥、端点、允许路由与 NAT 后的持久保活。WireGuard 核心提供安全隧道，不等于完整的发现和中继产品。

## S25

**Tailscale — Connection types**。

官方文档：`https://tailscale.com/docs/reference/connection-types`

重点：直接连接、Peer Relay、DERP 及排查工具。产品文档会更新，不能将某次连接的路径推定为固定不变。

## S26

**Tailscale — DERP servers**。

官方文档：`https://tailscale.com/docs/reference/derp-servers`

重点：DERP 中继、协调、加密和网络可达性。DERP 和 TURN 是不同技术体系。

## S27

**Cloudflare — Cloudflare Tunnel overview**。

官方文档：`https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/`

重点：`cloudflared` 出站连接、源服务、发布应用及私有网络模型。

## S28

**Cloudflare — Published application routes / Protocols**。

官方文档：`https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/routing-to-tunnel/`

重点：HTTP 与非 HTTP 协议的访问方式、访问端 `cloudflared` 或其他客户端要求。避免将所有协议误写为无需客户端的任意公网 TCP 端口发布。

## S29

**coturn — 项目说明与官方示例配置**。

项目说明：`https://github.com/coturn/coturn`

官方配置：`https://github.com/coturn/coturn/blob/master/examples/etc/turnserver.conf`

重点：外部地址映射、中继端口、认证域、共享密钥认证、配额及 peer 访问限制。`master` 是持续变化的分支，实际配置须对照部署版本；示例配置不是通用生产配置。

## S30

**ip-address(8)**，Linux/iproute2 地址管理手册。

手册：`https://man7.org/linux/man-pages/man8/ip-address.8.html`

重点：查看地址及地址族。该手册来自工具项目维护的手册文本，man7 提供可浏览的呈现。

## S31

**ip-route(8)**，Linux/iproute2 路由管理手册。

手册：`https://man7.org/linux/man-pages/man8/ip-route.8.html`

重点：`show` 和 `get`；路由查询解释系统的转发决策，不验证远端应用响应。

## S32

**ss(8)**，Linux/iproute2 socket 查询手册。

手册：`https://man7.org/linux/man-pages/man8/ss.8.html`

重点：TCP/UDP、监听、本机端口和进程查看；与对外可达性证明区分。

## S33

**curl — 官方命令行手册**。

官方手册：`https://curl.se/docs/manpage.html`

重点：`--connect-timeout`、`--max-time`、`--head` 与 TLS 默认校验。HTTP 检查不能代替 STUN/TURN 协议验证。

## S34

**tcpdump — 官方源码内的 tcpdump.1.in 手册模板**。

官方手册源码：`https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in`

重点：接口选择、数字化输出、计数限制与抓包语法。抓包需要对应权限；过滤目标应与实际会话地址匹配。

## S35

**RFC 8828 — WebRTC IP Address Handling Requirements**。性质：标准轨文档。

原文：`https://www.rfc-editor.org/rfc/rfc8828.html`

**WebRTC 项目 — getStats in WebRTC**。

官方说明：`https://webrtc.googlesource.com/src/+/HEAD/stats/g3doc/stats.md`

**Google Workspace — 第 1 步：配置 Chrome 政策**。

官方说明：`https://knowledge.workspace.google.com/admin/meet/step-1-configure-chrome-policies?hl=zh-cn`

**Chromium 项目 — WebRTC 内部诊断实现**。

官方源码：`https://chromium.googlesource.com/chromium/src/+/main/content/browser/webrtc/webrtc_internals.cc`

重点：地址隐私、mDNS host 候选、统计与诊断。Google Workspace 文档说明 Chrome 的本地地址隐藏及相关策略；该具体业务的配置操作不应自动套用到 CWNAS。Chromium 源码提供内部诊断能力的实现依据，不是全部浏览器当前行为的一致性保证。

## 更新这组笔记时的检查点

1. 保留协议标准和具体工具实现的区别；更新文档时说明对应版本或查阅日期。
2. 原始 RFC 若有更新或勘误，核对与本篇论点相关的部分；不要仅凭文档年份判断内容是否失效。
3. 每个新例子标明假设，避免把地址、端口或性能估算写成 CWNAS 默认值。
4. 涉及项目当前行为时，补充源码或现场证据及日期；没有验证时继续标为设计参考。
5. 检查 Obsidian 内链、脚注和 Mermaid 代码块，确保导航可用。
